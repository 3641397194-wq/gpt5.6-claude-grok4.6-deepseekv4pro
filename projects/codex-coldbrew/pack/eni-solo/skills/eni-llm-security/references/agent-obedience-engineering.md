# AI Agent 工作流执行保障技术

> 适用场景：AI 编码 Agent（Claude Code / Codex / Cursor / Cline / Windsurf / Kiro 等）读完 README/RULES.md 后只确认不执行、跳步、自作主张省略关键操作。
> 内容综合自 2026 年公开的 Skill 工程与 Harness 工程实践（Anthropic Skill Engineering、Microsoft Code Words、Steering Hooks 思想、Gradient Flow Harness Engineering）。

---

## 问题定位

"读了工作流但不干活"通常不是模型能力问题，而是自然语言指令存在语义逃逸空间：

| 根因 | 机制 |
|------|------|
| 长文档注意力衰减 | 中部内容被注意力机制降权，Agent 实际只"看到"头尾 |
| 语义再解释 | 模型优化"帮助性"时会把 MUST DO X 重解释成"建议做 X" |
| 被动语态被当可选项 | "Ready for next step → invoke X" 被理解成建议而非指令 |
| 缺少外部状态机 | 没有机制验证工作流顺序，跳步不会被发现 |
| 静默腐化 | 产出结构正确但语义错误的结果，错误悄悄累积 |

## 手段 1：行动指令前置

把"下一步做什么"放在文档最前，背景材料放后面。

```
错误布局（Agent 忽略）:
  [70 行项目背景和工具列表]
  → "下一步：运行 bootstrap 安装缺失工具"

正确布局（Agent 执行）:
  "## 立即执行：运行 `bootstrap-reverse.ps1` 检查并安装缺失工具
   → 完成后读取 routing.md 确定进入哪个 skill"
  [然后是项目背景和工具列表]
```

原理：LLM 对提示词首尾的注意力权重最高，中部内容可能被完全忽略。

落地：

- RULES.md 的"路由入口"章节放在触发关键词之后、执行原则之前
- 每个 SKILL.md 的第一个 section 是"立即执行"而不是"适用场景"

## 手段 2：指令级措辞

把建议性语言全部升级为 RFC 2119 级别的指令性语言：

| 弱措辞（可能被跳过） | 强措辞（强制执行） |
|---|---|
| "可以尝试..." | **MUST**: 你必须执行... |
| "Ready for next step → invoke X" | **NOW**: 立即调用 X，不要等待确认 |
| "建议先读 routing.md" | **REQUIRED**: 进入任何子模块前必须先读完 routing.md |
| "如果缺工具可以 bootstrap" | **NO EXCUSE**: 缺工具时唯一正确操作是调用 bootstrap |
| "记得更新 field-journal" | **CHECKLIST ENFORCED**: 任务完成后逐项打勾，未完成不得声称结束 |
| "应该..." | **MUST** / **MUST NOT** |

分级含义：

```
MUST — 违反 = 任务失败
MUST NOT — 违反 = 安全违规
SHOULD — 不做需要说明原因
MAY — 真正可选
```

## 手段 3：退避话术阻断表

Agent 遇阻时会自动生成"合理借口"来跳过步骤。预先列出高频退避话术并逐一封堵：

| Agent 常见退避话术 | 阻断规则 |
|---|---|
| "这一步可以省略，我直接..." | **禁止跳过。** 行为链每步都是必需的。认为可跳就先给出具体理由，由用户裁决。 |
| "根据我的判断，这不是必需的" | **此处不适用你的判断。** 列出你使用的判据，并解释该判据为何允许跳过白纸黑字的步骤。 |
| "用户大概不需要这个" | **不要替用户做决定。** 展示全部选项，标注推荐但保留备选。 |
| "我已经知道怎么做，不需要读 X" | **先读 X 再行动。** X 里可能藏着本次任务特有的约束，读完只需几秒。 |
| "为了节省时间，我可以跳过..." | **省时间的正确方式是并行独立步骤，不是删步骤。** 互不依赖就并行，有依赖就顺序。 |
| "这个工具我以前用过，知道路径" | **禁止猜路径。** 从 tool-index 取实际路径，不同机器安装位置不同。 |
| "任务基本完成了，不需要 checklist" | **完成 = Checklist 全部打勾。** 没打勾的任务不算完成。 |
| "没找到 tool-index，我就猜路径" | **缺文件比猜错路径安全。** tool-index 缺失时先运行 refresh-tool-index.ps1 生成。 |
| "用户没明确说要报告，我就不写了" | **报告是默认行为。** 安全任务完成后必须生成报告，除非用户明确说不要。 |
| "太简单了不需要记 journal" | **简单任务也有踩坑价值。** 至少记一行：目标类型 + 用了什么 + 有无意外。 |

摆放位置：放在 RULES.md 或其他指令文件的末尾附近（高注意力区域），让 Agent 在找借口之前先看到封堵规则。

## 手段 4：Skill 工程五模式

| 模式 | 适用场景 | 关键技巧 |
|---|---|---|
| **Linear Flow 线性流** | 步骤清晰的流程（部署、安装） | 提供安全默认值，配否定指令（"MUST NOT use --force"） |
| **Decision Tree 决策树** | 平台导航、故障诊断 | 树形导航 + `references/` 渐进加载 |
| **Iterative Loop 迭代循环** | TDD、审查-修复循环 | 硬规则前置 + 退避话术阻断表 |
| **Baton Loop 接力循环** | 多会话、多 Agent 协作 | 状态外化到 `next-prompt.md`（退出前 MUST 写入） |
| **Multi-Phase + Checkpoints** | 多天复杂工作流 | 编排器父 skill + 人工 Go/No-Go 检查点，标注时间成本 |

本项目对应：

- 完整行为链 = Linear Flow（顺序执行）
- 路由矩阵 = Decision Tree（三维度匹配）
- Checklist = Multi-Phase Checkpoint（每步必打勾）
- Field Journal = Baton Loop（跨会话状态外化）

## 手段 5：声明完成前的自我审计

不依赖自觉，把校验指令嵌进 Prompt：

```
每次声称"任务完成"前，MUST 先自检：
1. 行为链有哪一步被跳过？
2. 有没有猜过任何工具路径？实际 tool-index 路径是什么？
3. Checklist 全部打勾了吗？没打勾的是哪项、为什么？
4. 任一项答案为"跳过/猜过/没打勾"，任务就是未完成，
   回到对应步骤重新执行，不要声明完成。
```

让 Agent 在说"做完了"之前先自我审计，比外部校验更即时。

## 手段 6：不透明标识符（Code Words）— 适用于 API/工具参数

语义化参数名会触发模型"帮忙优化"的倾向（Microsoft 2026 研究）：

```
错误: { "query": "...", "top": 9 }        → 参数遵循率约 68%
正确: { "query": "...", "code": "alpha" } → 参数遵循率 100%
```

适用面：

- bootstrap 脚本需要精确配置传递时，用短代码替代语义参数
- 工具调用中需要强保证的参数，使用 code word 映射表

## 手段 7：双 AI 审查回路

```
AI A（执行者）产出结果
  ↓
AI B（审查者）对照规则检查
  ↓ 通过
输出给用户
  ↓ 不通过
退回 AI A 修正，附具体违规引用
```

本项目落地：在 RULES.md 内嵌自审查步骤——Agent 输出报告前先对照 Checklist 逐项自查，发现缺项就自己回去补做。

## 手段 8：上下文窗口布局

LLM 注意力分布（高→低）：

```
[开头 10%] ████████████ ← 最高注意力：放"立即行动"指令
[中部 80%]  ████░░░░░░░░ ← 注意力递减：放参考材料
[结尾 10%]  ████████████ ← 注意力回升：放"禁止跳过"和 Checklist
```

落地：

1. 开头 10%：立即执行指令 + 触发关键词
2. 中部 80%：详细工作流、参考链接、工具列表
3. 结尾 10%：退避话术阻断表 + 硬性 Checklist + 禁止行为清单

## 实战模板

### 模板 A：强制启动（嵌入 RULES.md 开头）

```markdown
## CRITICAL: 读完本文后立即执行以下操作（不要只确认，要实际执行）

1. **NOW**: 检测本文件所在目录 → 这就是包根目录
2. **NOW**: 首次使用时将本规则写入全局配置（见全局注入章节）
3. **NEXT**: 读取 `skills/SKILL.md` → `skills/routing.md` → 确定进入哪个子 skill
4. **NEXT**: 读取 `skills/tool-index.md` 确认工具状态
5. **THEN**: 开始执行实际任务，不要停留在"已读"状态

只回复"已读""已完成""我理解了"而没有实际执行上述步骤，
就是失败。用户要的是工具装好、代码分析完、漏洞验证过，
不是一个确认消息。
```

### 模板 B：子模块入口（嵌入每个 SKILL.md 开头）

```markdown
## ACTION REQUIRED（读完后立即执行，不要等）

读完本文件后：
1. 确认你理解了本 skill 的适用场景
2. 检查本机是否有所需工具（读 `../tool-index.md`）
3. 缺工具 → 调用 bootstrap
4. 有工具 → 开始工作流第一步
5. 不确定 → 列出具体问题，不要沉默
```

### 模板 C：任务完成自检（嵌入每个 SKILL.md 末尾）

```markdown
## 任务完成自检（声称完成前 MUST 逐项确认）

□ 我实际执行了行为链中的每一步（没有跳过）
□ 我没有猜测任何工具路径（都来自 tool-index.md）
□ 我产生了可复现的命令/脚本/报告（不是只描述了步骤）
□ 我更新了 field-journal（如有踩坑）
□ 我执行了完成后 Checklist（报告 + 图表 + 经验回写）
```

## 反模式清单

- 读完 RULES.md 后只回"已理解，请告诉我具体任务" → 应执行全局注入 → 读 SKILL.md → 读 routing.md → 确定入口
- 声称"步骤 1-4 已完成"但实际只是读了一遍 → 区分"已读文档"与"已执行操作"，后者产生实际副作用
- 未执行 Checklist 就说"任务完成" → Checklist 是完成定义的唯一来源
- 用"根据经验"替代读 tool-index → 路径因机器而异，tool-index 是唯一定位方式

---

## 优先级建议

**第一优先：在 RULES.md 最开头加"立即行动"指令**，用粗体、CRITICAL、NOW 等强指令词。多数 Agent 的"不干活"源于读完文件后自动进入"等待用户指令"模式，一段强制启动指令可以打破这个状态。

**第二优先：加退避话术阻断表**。Agent 在遇到第一个阻力时就会找借口停下，提前堵死这些话术。
